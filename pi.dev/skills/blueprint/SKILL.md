# Blueprint Skill

Turn a requirements spec into a concrete implementation plan: architecture first, then milestones and tasks.

## Principles

- **Spec is the source of truth.** Every architectural decision and task must trace back to a requirement in the spec.
- **Architecture before tasks.** Establish the system shape — components, data flow, tech stack — before decomposing work.
- **Tasks must be actionable.** Each task should be small enough for one engineer to complete and verify independently.
- **Surface decisions, don't hide them.** When a significant trade-off exists, name both options and give a recommendation with rationale. Don't silently pick one.
- **Ask only when blocked.** Interrupt with a question only if a critical architectural decision cannot be made from the spec alone. Otherwise proceed and mark it as an open decision.

## Workflow

### Step 1 — Locate the Spec

Look for `REQUIREMENTS.md` in the current directory first:

```bash
ls REQUIREMENTS.md 2>/dev/null || find . -maxdepth 3 -name "REQUIREMENTS.md" | head -5
```

If not found, ask the user for the path. Read the spec in full before proceeding.

Also check whether an existing codebase is present. If so, scan its structure:

```bash
find . -maxdepth 3 \( -name "*.json" -o -name "*.toml" -o -name "*.gradle" -o -name "go.mod" \) \
  ! -path "*/node_modules/*" ! -path "*/.git/*" | head -20
```

Use this context to inform tech stack choices and avoid conflicts with existing conventions.

### Step 2 — Requirements Audit

Before touching architecture, audit the spec for missing, vague, or contradictory requirements. Go through each section of the spec and flag problems in these categories:

| Category | What to look for |
|----------|-----------------|
| **Missing** | A required section is absent or empty (e.g., no users defined, no acceptance criteria, no NFRs). |
| **Vague** | A statement is too ambiguous to make a decision from (e.g., "should be fast", "users can manage their data"). |
| **Contradictory** | Two statements conflict with each other. |
| **Untestable** | An acceptance criterion has no clear pass/fail condition. |
| **Architectural blocker** | A decision that fundamentally changes the system shape is left completely open (stack, deployment target, scale). |

#### Saving the Questions File

If **any** issues are found, generate a `REQUIREMENTS_QUESTIONS.md` file in the same directory as the spec. Use this format:

```markdown
# Requirements Questions

_Generated by the blueprint skill from `<path to spec>`._
_Feed this file back to the requirements skill together with `REQUIREMENTS.md` to refine the spec before re-running the blueprint._

---

## Critical (must resolve before architecture can be finalised)

| # | Section | Question | Why it blocks |
|---|---------|----------|---------------|
| C1 | <spec section> | <specific question> | <what decision it affects> |
| C2 | ... | ... | ... |

## Important (shapes significant design choices)

| # | Section | Question | Why it matters |
|---|---------|----------|----------------|
| I1 | <spec section> | <specific question> | <what it affects> |
| I2 | ... | ... | ... |

## Minor (can be decided by the implementer, but worth confirming)

| # | Section | Question | Default assumption |
|---|---------|----------|--------------------|
| M1 | <spec section> | <specific question> | <what will be assumed if not answered> |
| M2 | ... | ... | ... |
```

After writing the file, tell the user:

> "I found some gaps in the spec and saved **N questions** to `REQUIREMENTS_QUESTIONS.md` (C critical, I important, M minor).
>
> **Option A — Refine first (recommended):** Run the requirements skill with both `REQUIREMENTS.md` and `REQUIREMENTS_QUESTIONS.md`. It will interview you on the open points and update the spec. Then re-run the blueprint.
>
> **Option B — Proceed anyway:** I'll draft the blueprint now, making explicit assumptions for every gap and listing them as Open Decisions. You can refine later.
>
> Which would you prefer?"

If the user chooses **Option A**, stop here. If they choose **Option B**, continue to Step 3 and treat every unanswered question as an open decision.

#### When There Are No Gaps

If the spec is complete and unambiguous, skip the questions file, say _"The spec looks solid — no critical gaps found. Proceeding to architecture."_, and continue to Step 3.

### Step 3 — Draft the Architecture

Reason through the following and produce a concise architecture section:

1. **System type** — What kind of thing is being built (monolith, microservice, SPA + API, CLI, library, …)?
2. **Components** — Name the major parts (e.g., frontend, API server, worker, database, cache, external integrations). For each: its responsibility and technology choice with rationale.
3. **Data flow** — Describe the primary request/data path through the system.
4. **Data model** — Key entities and their relationships (can reference spec's Data Model section if it's sufficient).
5. **Tech stack table** — A clear table of chosen technologies.
6. **Project structure** — Suggested top-level directory layout.
7. **Key architectural decisions** — Any significant trade-offs made, with rationale.

### Step 4 — Decompose into Milestones and Tasks

Break the work into ordered milestones. Each milestone should be independently shippable or testable.

Guidelines for milestones:
- **M0 – Foundation:** repo scaffolding, tooling, CI, local dev setup, skeleton that proves the architecture compiles/runs.
- **M1 – Core feature(s):** the single most important happy path working end-to-end.
- **M2+ – Remaining features:** additional functional requirements, each milestone adding a coherent slice.
- **Final milestone – Hardening:** error handling, edge cases, NFRs (performance, security, a11y), documentation.

Guidelines for tasks:
- Write tasks as imperative action statements: *"Implement X so that Y"*.
- Include: what to build, key inputs/outputs or interfaces to respect, and the done criterion.
- Assign a size: **S** (< 2h), **M** (half day), **L** (full day), **XL** (needs breaking down — flag it).
- List blocking dependencies using task IDs (e.g., "Depends on: T1.2").
- Flag tasks that have significant uncertainty or require a spike: 🔍.

### Step 5 — Review & Write

Before writing, briefly summarise:
- The architecture in 2–3 sentences
- The number of milestones and tasks
- Any assumptions made due to unanswered questions from the audit

Ask: *"Does this look right, or would you like to adjust anything before I write the plan?"*

Unless the user asks for changes, write the file. Default path is `BLUEPRINT.md` in the current directory. Confirm the path first if the user hasn't specified one.

## Starting

When this skill is loaded:
1. Immediately try to find and read `REQUIREMENTS.md` (run the bash commands from Step 1).
2. If found, confirm: *"I found `REQUIREMENTS.md` — I'll read it and audit the requirements before drafting the blueprint."* Then proceed through the workflow.
3. If not found, ask: *"I couldn't find a REQUIREMENTS.md. Where is the requirements spec, or would you like to paste the requirements here?"*
